### 2. Concurrent writes evaluated and deliberately NOT adopted

The headline v0.7.0 feature is optimistic concurrency: writers build against
private COW snapshots and validate at commit instead of serializing behind a
writer lock. Benchmarked rather than assumed, because mini's write path is a
**single** batching writer goroutine — there is no writer contention for OCC
to relieve.

| workload (M3, 8 cores, medians) | single-writer | concurrent (OCC) |
|---|---|---|
| batched durable visit (current design) | **13.1µs** | 98.9µs (7.6× worse) |
| unbatched parallel commit, durable | 676µs | 776µs |
| unbatched parallel commit, sync-never | 12.2µs | 11.4µs (7% better) |

**Root cause of the 7.6× regression** (verified in bytdb's `seqalloc.go`):
under OCC, sequence/identity draws become non-transactional (Postgres
semantics — gap-tolerant, so parallel inserts don't all collide on one
counter key). `NextSeq` then routes through `seqPut` → its own
`kv.Update(...)` transaction instead of riding our batch txn, allocating in
blocks of `seqAllocBatch = 32`. A 256-row batch therefore pays ~9 durable
commits instead of 1.

Conclusion: **batching, not parallelism, is what this workload needs** — the
cost is the fsync, and only amortizing it across rows removes it. OCC also
gives ~nothing for a single-row insert shape (bytdb's own README measures
11.4µs vs 11.2µs parity). bytdb's docs agree: "stay with the default when
writes are occasional or naturally serial."

Recorded permanently in the `store` package doc (`store/store.go`, "# Write
mode" section) so the decision isn't re-litigated.

### 3. Quiet request logging under `-bench`

`rweb.RequestInfo` `fmt.Printf`s a line per request with no switch of its own.
Under `go test -bench` that interleaved with the benchmark's own stdout and
buried/mangled the `ns/op` lines (the parallel benchmarks' results were being
lost entirely to `grep '^Benchmark'`).

Fix: register the middleware behind `opts.Verbose` in `newServer`
(`web/server.go`), and have `startTestServer` set `Verbose: !isBench` via a
`_, isBench := t.(*testing.B)` type assertion. Net effect:

- production (`StartWebServer`) — logs, unchanged (already set `Verbose: true`)
- tests — logs kept; `go test` only surfaces them on failure, which is exactly
  when they're wanted
- benchmarks — quiet

Checked that rweb's `Verbose` gates logging only (plus a ReadyChan-capacity
warning), no behavioral coupling.

## Benchmarking gotchas learned

- **Cold-start outlier**: `BenchmarkHTTPRootParallelDurable`'s *first*
  `-count` iteration reads ~250–350µs before settling to ~40µs. Reproduces on
  v0.6.4 too — temp-dir/page-cache warm-up, not a regression. Use
  `-benchtime 3s` or discard the first sample.
- `grep '^Benchmark'` silently drops result lines when anything else writes to
  stdout mid-run (the reason for the logging fix above).

## Key API notes (v0.7.0, for future reference)

- `bytdb.WithConcurrentWrites()` — opt-in OCC. Snapshot isolation by default;
  `WriteTxnSerializable` / `BeginSerializable` opt a txn up to SERIALIZABLE by
  also tracking reads.
- Conflicts surface as `bytdb.ErrTxConflict` (SQLSTATE 40001 on the wire).
  **The caller retries** for embedded `WriteTxn` / one-shot writes — wrap in a
  loop on `errors.Is(err, bytdb.ErrTxConflict)`; the closure re-runs from a
  fresh snapshot. Autocommit SQL statements get 3 silent server retries;
  explicit `BEGIN … COMMIT` blocks are never retried server-side.
- Under OCC, sequence/identity draws are **non-transactional and
  gap-tolerant** (values burned on abort; `SetSeq` takes effect immediately).
  This is what makes parallel inserts into one table viable — and what makes
  it a poor fit for a batched single writer.
- DDL never runs inside a txn in either mode; under OCC it tries
  optimistically then escalates to a brief exclusive stall, so it always makes
  progress and never returns 40001 (but conflicts every in-flight txn).
- Read path is unchanged in both modes: reads never block, always on immutable
  snapshots.
- Full contract: `docs/concurrency.md` in the bytdb module.
